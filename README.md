# Вместе

Сервис для свадебных организаторов: приглашения, рассадка, вход гостей по QR-коду.

Состояние: **этап 1 из 8** — работает вход в зал (самый рискованный сценарий).
План целиком в [PLAN.md](./PLAN.md), журнал работы в [PROGRESS.md](./PROGRESS.md).

## Что уже работает

- Вход гостя по QR: сканирует код → вводит имя → видит свой стол.
  Поиск переживает опечатки, уменьшительные имена и латиницу.
- Панель организатора: гости, импорт CSV из Excel, рассадка, печать.
- Печатный план Б: QR-табличка и список «имя → стол» на бумагу.

## Запуск

Нужны Node 20+ и PostgreSQL 15+ с расширениями `pg_trgm`, `citext`, `pgcrypto`.

```bash
npm install
cp .env.example .env          # и вписать свои DATABASE_URL и AUTH_SECRET

createdb vmeste_dev
createdb vmeste_test

npx prisma migrate dev        # схема
npm run db:seed               # два мероприятия с гостями
npm run dev
```

Сид печатает коды входа. Организатор — `planner@example.com` / `password123`.

Через Docker (если он есть): `docker compose up -d` поднимет PostgreSQL на порту
5433 и MinIO на 9000; в `.env` нужно указать порт 5433.

## Развёртывание: обязательные условия

1. **Долгоживущий процесс Node**, не serverless. На этапе 6 появится SSE
   и `LISTEN/NOTIFY` — им нужен процесс, который живёт между запросами.
2. **`NEXT_PUBLIC_APP_URL`** должен указывать на внешний адрес: он попадает
   в QR-коды и именные ссылки. Хардкода хоста в коде нет.
3. **Прогреть сервер до приезда гостей.** Первый запрос после старта идёт
   2,5–4 секунды, дальше 20 мс.
4. Перед свадьбой распечатать `/app/e/<id>/print` — обе страницы.

### Три вещи, которые надо знать до правок

**Гостевые страницы входа написаны без React.** App Router грузит рантайм
React на любой странице — 173 КБ при бюджете 150 КБ на всё. `/e/*` собираются
строкой в `src/server/guest-html/` и весят 3 КБ. Не переписывайте их
на компоненты: на площадках связи почти нет, и этот запас — не оптимизация
ради оптимизации.

**В БД ходят только репозитории.** Каждая дочерняя сущность ссылается
на родителя парой `(eventId, id)`, поэтому связать данные двух мероприятий
физически невозможно. Плюс `db.ts` бросает на запросе без фильтра по `eventId`.

**Имена гостей нормализуются при записи.** `Guest.searchKey` и `GuestAlias`
заполняются в `repositories/guests.ts`. Если писать гостя мимо репозитория,
он не найдёт себя на входе.
