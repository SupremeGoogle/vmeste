Проблемы с высоким приоритетом

P1 — исправить до расширения эксплуатации. P2 — исправить в ближайшем цикле. Приоритет обозначает возможный ущерб и воспроизводимый механизм, а не свидетельство произошедшего инцидента.

P1 · приглашения

Одинаковая ссылка может открыть другую свадьбу

Уникальность slug задана внутри организации, а публичные страницы ищут опубликованное мероприятие только по slug. Две разные организации могут создать одинаковый адрес. Публичная загрузка выбирает первое мероприятие; ответы гостей могут попасть в чужую свадьбу.

Основание: prisma/schema.prisma:387; src/server/repositories/events.ts:44; src/server/repositories/invites.ts:479; src/app/i/[eventSlug]/join/route.ts:45.

Исправление: использовать глобально уникальный публичный идентификатор или включить организацию в маршрут и поиск. Перед миграцией проверить существующие коллизии и сохранить старые ссылки через однозначные перенаправления. Тест: две организации с одинаковым slug никогда не получают приглашения и ответы друг друга.

P1 · фотографии

Проверенный оригинал остаётся доступен для повторной записи

Гость получает подписанный PUT на 15 минут. Обработка читает файл, преобразует его и записывает результат по тому же ключу, который затем сохраняется в базе. Пока ссылка действительна, повторный PUT может заменить уже обработанный оригинал после проверок. Это обходит обработку и удаление EXIF для заменённого содержимого; миниатюра и оригинал могут расходиться.

Основание: src/server/storage/s3.ts:180–191; src/server/services/photos.ts:164,174,206. Подтверждено чтением кода; повторная загрузка в реальное хранилище не выполнялась.

Исправление: выдавать загрузку на временный ключ, а проверенный результат записывать на отдельный серверный ключ, недоступный по гостевому PUT. В базе сохранять только финальный ключ. Тест: повторная запись во временный объект не меняет утверждённый оригинал и миниатюру.

P1 · доступ администратора

Параллельные проверки 2FA теряют попытки и повторно принимают код

Проверка читает счётчик, последний TOTP-шаг и резервные коды, затем отдельно обновляет запись. Одновременные запросы могут прочитать одинаковое состояние, принять один резервный/TOTP-код дважды и затереть увеличение счётчика ошибок.

Основание: src/server/admin/access.ts:147–183. Проверка функции с базой, имитированной в памяти: 20 параллельных неправильных кодов оставили счётчик 1 без блокировки; один TOTP и один резервный код были приняты по два раза. Реальная база и аккаунты не использовались.

Исправление: сериализовать проверку и изменение состояния одной записи: транзакция с блокировкой строки либо проверяемое атомарное обновление. Счётчик увеличивать атомарно. Успешное потребление кода должно происходить ровно один раз. Добавить тесты параллельных запросов.

P1 · тестовые данные

Интеграционные тесты могут очистить обычную базу

Тестовый helper использует TEST_DATABASE_URL ?? DATABASE_URL, затем удаляет все организации и пользователей. При отсутствии отдельной тестовой настройки запуск интеграционного набора может очистить базу приложения.

Основание: src/tests/helpers/db.ts:9,14–15; аналогичный fallback есть в создании клиента базы для тестового режима.

Исправление: требовать отдельный TEST_DATABASE_URL и прекращать запуск, если он отсутствует или совпадает с основным адресом. Желательно использовать изолированную одноразовую базу. Во время этого ревью выполнялись только выбранные тесты без очистки реальной базы.

P1 · время мероприятия

Время новой свадьбы зависит от часового пояса сервера

Дата из формы преобразуется через new Date(`${dateRaw}T${timeRaw}:00`) без часового пояса площадки. На сервере UTC введённые 16:00 становятся 16:00 UTC и отображаются как 19:00 в Москве. Это влияет на приглашение и последующее расписание.

Основание: src/app/(app)/app/events/new/page.tsx:55; default часового пояса в создании мероприятия — Europe/Moscow.

Исправление: сначала определить пояс площадки, затем преобразовать её локальные дату/время в UTC существующим специализированным helper. Тестировать одинаковую форму при разных TZ сервера и на переходах летнего времени для поддерживаемых регионов.

P2 · английский язык

Время после полудня теряет AM/PM

Intl для en-US возвращает 12-часовое время, но helper сохраняет только hour/minute и отбрасывает dayPeriod. Например, 13:00 отображается как 01:00 без PM.

Основание: src/lib/format-datetime.ts:23–39,51–53. Использовать полный результат форматирования времени либо явно выбрать 24-часовой формат. Проверки: полночь, полдень, 13:00, разные часовые пояса.

P2 · перевод гостевых сценариев

Английская свадьба сохраняет русские элементы интерфейса

Главная QR-страница форматирует дату через ru-RU; существующие гостевые компоненты содержат русские кнопки и подсказки. Командная страница не выбирает Event.language, не передаёт язык в DayPlanList и содержит русские заголовки. Новые панели оформления переведены, но весь существующий гостевой интерфейс пока нельзя назвать полностью переведённым.

Основание: src/app/(guest)/g/[shortCode]/page.tsx:29; src/app/(guest)/g/[shortCode]/guest-app.tsx; src/components/guest/entry.tsx; src/app/(guest)/team/[token]/page.tsx:36,77.

Исправление: передавать язык мероприятия по всему гостевому сценарию, включая фото, подарки, ошибки, пустые состояния, письма и план команды. Проверять последовательный путь англоязычного гостя, а не только главную страницу.

P2 · работа без сети

Service worker обслуживает старые адреса гостевых страниц

Кеш распознаёт только /e/..., тогда как актуальный гостевой интерфейс находится на /g/.... Поэтому текущий код не подтверждает обещание, что гость сможет повторно открыть свой стол без связи после посещения новой страницы.

Основание: public/sw.js:31,52 и текущий маршрут src/app/(guest)/g/[shortCode]/. Реальное отключение сети на телефоне не тестировалось.

Исправление: определить поддерживаемый offline-сценарий для новой страницы и нужных ресурсов. Если сохраняется личная рассадка, ограничивать её конкретным гостем и предусмотреть очистку на общем устройстве. Не кешировать общий список гостей как публичный ресурс.

P2 · удаление мероприятия

Удаление записи не планирует удаление объектов хранилища

Удаление мероприятия выполняет удаление в базе. Отдельной гарантированной задачи очистки фото в этой операции нет. Если периодическая очистка опирается на существующие события, объекты удалённой свадьбы больше не попадут в её выборку.

Основание: src/server/repositories/events.ts:124–128 и вызывающий обработчик панели.

Исправление: сохранять задачу очистки/outbox до удаления связей, удалять объекты с повторными попытками и учитывать сбой хранилища. Тест: удаление события плюс временный отказ S3 в итоге не оставляют потерянные объекты.

P2 · повторное применение сценария

Подсказка обещает более сильную защиту от дублей, чем код

Существующий сценарий тайминга определяет дубли по времени и заголовку. После редактирования этапа повторное применение возвращает оригинальный этап как новый. Подсказку «не повторятся» пользователь может понять как сохранение результата предыдущего применения.

Основание: src/server/services/timing-templates.ts:20–23; src/components/timing/timing-templates.tsx.

Исправление: хранить происхождение этапа из шаблона либо явно предупреждать, что защита относится только к полностью совпадающим этапам. Новые четыре оформления лишь показывают программу и не добавляют этапы.

SEO и GEO

Что уже есть и что улучшить

Публичные страницы / и /en имеют доступный серверный текст, языковые альтернативы, canonical и FAQ-разметку. В проекте есть публичные тематические страницы и статьи; их наличие учтено при ревью. Закрытые свадьбы и гостевые страницы не следует превращать в поисковые посадочные страницы.

P2 · sitemap Для общих страниц src/app/sitemap.ts:18 выставляет lastModified текущим временем при генерации. Это не дата реального изменения содержимого. Использовать дату изменения контента либо убрать поле; для статей уже используются published/updated. Google рекомендует передавать достоверные даты изменения: официальное руководство по sitemap.

Для присутствия в AI-функциях поиска сохранять полезный публичный текст, внутренние ссылки, точные описания возможностей и разметку, совпадающую с видимым содержимым. Специальный «AI-файл» или отдельная схема не требуются; обычные основы SEO остаются применимыми. Это рекомендации для Google Search, а не гарантия упоминаний всеми AI-системами: Google: AI features and your website.

Если используется noindex, робот должен иметь возможность прочитать его: запрет обхода в robots.txt сам по себе не гарантирует удаления URL из индекса. Для личных данных основной защитой остаётся контроль доступа. Проверить сочетания правил для /g, /i и /team: Google: block indexing.

Следующая проверка: Search Console на реальном домене, sitemap/canonical/hreflang в опубликованных ответах, валидность разметки и совпадение FAQ с интерфейсом, мобильные показатели загрузки. Изолированная локальная проверка не измеряет позиции, индексацию и реальные Core Web Vitals.
